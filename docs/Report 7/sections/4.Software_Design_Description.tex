\part{Software Design Description}

\section{Architecture Diagram}

\subsection{System Architecture}

The Frevia system follows an N-layer architecture, separating the client applications, presentation layer, business logic layer, data access layer, shared library layer, and external integration systems (Figure~\ref{fig:arch:overall}). The system also natively integrates with PostgreSQL, Cloudinary, Stripe, Google OAuth 2.0, Nodemailer, Infisical, and local Python FastAPI AI microservices backed by Ollama LLM.

\kfig{0.95\textwidth}{images/architecture/frevia-overall-architecture}{System Architecture Diagram}{fig:arch:overall}

\subsubsection*{Client Application}
Frevia delivers a unified, responsive web application catering to five actor roles: Guest, Client, Freelancer, Expert, and Administrator.
\begin{itemize}[leftmargin=*]
    \item \textbf{Web Client:} Developed with Next.js 16 (React 19) and TypeScript utilizing the App Router architecture. It consists of:
    \begin{itemize}[leftmargin=*]
        \item \textit{Pages and Screens:} Built with React Server Components (RSC) for optimal search engine indexing and rapid initial page loads, complemented by Client Components for interactive user interfaces. Styled using TailwindCSS 4 and the \texttt{@repo/ui} component library (based on shadcn/ui), and localized into English and Vietnamese via \texttt{next-intl}.
        \item \textit{Hooks and State Management:} Driven by TanStack Query (React Query) for server state caching, background revalidation, and optimistic mutations. Client-side form validation is managed via \texttt{react-hook-form} paired with Zod schemas.
        \item \textit{API Services (\texttt{apiRequests/}):} A typed HTTP client layer encapsulating \texttt{lib/http.ts}. It automatically binds JWT access tokens to request headers, transparently handles token refreshes upon expiration, and interfaces with the Socket.io client for real-time messaging and notifications.
    \end{itemize}
\end{itemize}
The client application transmits requests exclusively over HTTPS REST APIs and displays returned responses. It contains no direct database access logic and enforces no authoritative business rules.

\subsubsection*{Presentation Layer}
The Presentation Layer is implemented within the NestJS 11 Web Server Application (\texttt{apps/api}). It serves as the entry boundary for incoming client requests and real-time events:
\begin{itemize}[leftmargin=*]
    \item \textbf{Controllers:} Expose structured RESTful API endpoints (mounted under \texttt{/api}), receive client requests, bind validated request payloads, and delegate processing to domain services.
    \item {\sloppy \textbf{Authentication and Authorization Guards:} Intercept requests to verify JWT tokens (\texttt{Access\allowbreak{}Token\allowbreak{}Guard}) and enforce role and fine-grained permission checks (\texttt{Permission\allowbreak{}Guard}).\par}
    \item \textbf{Validation and Serialization:} Validates incoming request payloads using shared Zod DTOs and sanitizes outgoing responses using the global \texttt{ZodSerializerInterceptor}.
    \item \textbf{Socket.io Gateway:} Manages real-time bidirectional WebSocket connections for peer-to-peer conversations and immediate notification pushes.
\end{itemize}

\subsubsection*{Business Logic Layer}
The Business Logic Layer represents the core of the Frevia platform, encapsulating business rules, ownership verifications, and deterministic domain state machines across 33 route modules:
\begin{itemize}[leftmargin=*]
    \item \textbf{Authentication and Access Control Module:} Manages user registration, OTP verification, credential login, Google OAuth federated sign-in, token refresh, device sessions, roles, and granular permissions.
    \item \textbf{User and Profile Management Module:} Handles administrator user accounts, account profiles, freelancer professional portfolios, CV uploads, and expert consultation profiles.
    \item \textbf{Job and Proposal Management Module:} Governs client job postings, faceted job browsing, bookmarking, freelancer proposal submissions, and proposal acceptance/rejection workflows.
    \item \textbf{Contract and Milestone Module:} Enforces contract lifecycle transitions (awaiting payment, pending signature, active, completion, cancellation, rejection) and sequential milestone workflows.
    \item \textbf{Payment and Escrow Module:} Integrates Stripe Checkout for milestone escrow funding, platform fee collections, dispute fee handling, and automated Stripe Connect payouts to freelancer bank accounts.
    \item \textbf{Communication and Community Module:} Facilitates real-time direct messaging, multi-category discussion forums, post interactions, and automated user notification feeds.
    \item \textbf{Dispute Arbitration Module:} Provides formal dispute filing, evidence attachment, and administrator arbitration workflows.
\end{itemize}

\subsubsection*{Data Access Layer}
The Data Access Layer encapsulates persistence logic using the Repository Pattern, Prisma 7 ORM, and the native PostgreSQL adapter (\texttt{@prisma/\allowbreak{}adapter-\allowbreak{}pg}):
\begin{itemize}[leftmargin=*]
    \item \textbf{Repositories:} Implement dedicated query methods, data filtering, pagination helpers, and soft-delete semantics (\texttt{deletedAt}). Controllers and services are strictly decoupled from raw database queries.
    \item \textbf{Transaction Management:} Wraps complex multi-table workflows (such as escrow fund transfers, contract creation, and user onboarding cascades) inside atomic \texttt{\$transaction} blocks to maintain absolute relational integrity.
\end{itemize}

\subsubsection*{Shared Library Layer}
The Shared Library Layer provides shared definitions and cross-cutting utilities utilized across the application tiers:
\begin{itemize}[leftmargin=*]
    \item \textbf{Contract Single Source of Truth (\texttt{@shared/types}):} Monorepo package defining shared Zod validation schemas, TypeScript interfaces, system constants, database enumerations, and standardized error codes.
    \item \textbf{Backend Cross-Cutting Infrastructure (\texttt{src/shared}):} Contains global exception filters, authentication decorators, Cloudinary storage wrappers, Nodemailer integration, and the shared Prisma client service.
\end{itemize}

\subsubsection*{Data Storage}
\begin{itemize}[leftmargin=*]
    \item \textbf{PostgreSQL Database:} Stores all persistent platform data across 71 relational domain models and 43 enumerations, maintaining relational integrity with foreign keys, compound indexes, and audit timestamps.
    \item \textbf{Cloudinary Object Storage:} Dedicated cloud repository storing binary multimedia files, including user profile avatars, citizen identity document photographs (CCCD), candidate resumes, and contract deliverable archives.
\end{itemize}

\subsubsection*{External Systems and Internal AI Services}
\begin{itemize}[leftmargin=*]
    \item \textbf{Google OAuth 2.0:} Facilitates federated single sign-on. The frontend retrieves a Google authorization credential, which the backend verifies to establish an authenticated Frevia session.
    \item \textbf{Stripe:} Processes online financial transactions, managing escrow funding via Stripe Checkout, platform fee collection, dispute deposits, and automated freelancer payouts via Stripe Connect. Status updates are synchronized securely via cryptographic webhooks.
    \item \textbf{Internal AI Microservices (FastAPI \& Python):}
    \begin{itemize}[leftmargin=*]
        \item \textit{eKYC ID Verification (\texttt{id-verification}, port 8001):} Employs RapidOCR for card text extraction, UltraFace and ArcFace (ONNX Runtime) for facial detection and biometric embeddings, and MediaPipe for liveness detection to detect fraudulent identity documents.
        \item \textit{Section-Aware CV and Job Matching (\texttt{cv-matching}, port 8000):} BGE-M3 embeddings, ChromaDB vector indexing, and local Ollama LLM inference to parse candidate CVs and compute semantic candidate-to-job matching scores.
        \item \textit{AI Content Moderation (\texttt{ai-moderation}, optional external service on port 8002):} Scores forum posts and comments when \texttt{AI\_\allowbreak{}MODERATION\_\allowbreak{}URL} is set, falling back to \texttt{APPROVED} when unavailable.
    \end{itemize}
    \item \textbf{SMTP Mail Service (Nodemailer):} Delivers transactional notifications, one-time passwords (OTP), and contract status alerts.
    \item \textbf{Infisical:} Secure secrets manager that injects environment variables and credentials into application containers at startup.
\end{itemize}

\subsubsection*{Request-Response Data Flow}
A typical user request originates on a Next.js Page or Screen, triggers a TanStack Query hook, and invokes a typed API method in \texttt{apiRequests/}. The service binds the JWT access token and issues an HTTPS REST call to the NestJS backend. The request passes through the \texttt{AccessTokenGuard}, \texttt{PermissionGuard}, and Zod DTO validation before reaching the appropriate Controller. The Controller delegates execution to the Service Layer, which validates business rules and state machines, then commands the Repository to execute queries through Prisma 7 to PostgreSQL. The resulting entity follows the reverse path, is sanitized by the Zod serializer interceptor, and is returned as a uniform JSON response to update the client-side cache and re-render the user interface. Real-time events follow an asynchronous parallel path via the Socket.io Gateway.

\subsection{Package Diagram}
\label{subsec:package-diagram}

The Frevia repository is organized as a high-cohesion monorepo managed with \textbf{pnpm workspaces} and \textbf{Turborepo} (Figure~\ref{fig:arch:packages}). This structure cleanly separates the presentation tier (\texttt{apps/web}), the application tier (\texttt{apps/api}), the shared workspace packages (\texttt{packages/*}), and the independent AI microservices (\texttt{ai-services/}).

\kfig{0.95\textwidth}{images/architecture/frevia-package-diagram}{Package diagram}{fig:arch:packages}

\subsubsection*{Monorepo Architecture Rules}
The monorepo enforces four key architectural rules illustrated in Figure~\ref{fig:arch:packages}:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Strict Downward Dependencies:} Applications (\texttt{apps/web} and \texttt{apps/api}) depend on shared packages (\texttt{packages/*}); a shared package never imports code or types from an application.
    \item \textbf{Module Isolation:} Domain route modules inside \texttt{apps/api/src/routes/} are strictly decoupled and never import controllers, services, or repositories from sibling modules. Cross-module data flows exclusively through database relationships at the Prisma ORM schema level.
    \item \textbf{Universal Configuration:} Common configurations for linting (\texttt{@repo/eslint-config}) and TypeScript compilation (\texttt{@repo/typescript-config}) are inherited by all workspaces to guarantee uniform code quality.
    \item \textbf{Independent AI Service Boundaries:} Containerized Python-based AI microservices (\texttt{id-\allowbreak{}verification} and \texttt{cv-\allowbreak{}matching} backed by Ollama) reside in \texttt{ai-services/}, alongside an optional external \texttt{ai-\allowbreak{}moderation} endpoint, and communicate with the backend via standard HTTP REST calls, maintaining complete independence from the TypeScript pnpm workspaces.
\end{enumerate}

\section{Entity Relationship Diagram (ERD)}

Frevia persists every domain object in a single PostgreSQL database whose schema is
declared with Prisma 7 in \texttt{apps/api/prisma/schema.prisma}. The schema contains
71 models together with 43 enumerations, every table has a surrogate integer primary
key generated by the database (nine membership tables use a composite key instead), and
deletion is either restricted by a foreign-key rule (identity and money-related rows are
never removed) or implemented as a soft delete through a \texttt{deletedAt} column
(content that an administrator must be able to restore: jobs, forum categories and posts,
skills, banners, contract term templates). Binary files are not stored in the database:
only their Cloudinary URL is kept in the owning row.

Figure~\ref{fig:db:erd} shows the entity--relationship diagram of the whole schema.
Every table is drawn as a frameless box: the header carries the table name, each of the
following rows is one column, and the key columns are flagged with \texttt{PK} (primary
key) or \texttt{FK} (foreign key). A relationship is a line that leaves the many-side
table with a crow's foot and ends on the one-side table with a single bar, so it reads
from the row that holds the foreign key to the row it references.

\kfig{0.95\textwidth}{images/database/erd}{Entity--relationship diagram of the Frevia database}{fig:db:erd}

\subsection{Table Relationships}

The 71 tables are grouped into nine families; inside a family the relationships are
one-to-many, and membership tables carry the many-to-many links:

\begin{itemize}[leftmargin=*]\sloppy
    \item \textbf{Identity and access} --- \texttt{User} is the root of the schema and now also carries a required \texttt{roleId} that points to its primary \texttt{Role}; \texttt{UserRole} still links an account to any additional \texttt{Role}, and \texttt{RolePermission} links a role to a \texttt{Permission}, which yields the RBAC model enforced by the guards. Authentication adds \texttt{Session} (one row per device), \texttt{VerificationCode} (OTP for registration and password reset), \texttt{OauthAccount} (Google login), \texttt{TwoFactorAuth} and \texttt{UserSetting}.
    \item \textbf{Profiles} --- \texttt{Profile} is shared by every account; \texttt{FreelancerProfile} and \texttt{ClientProfile} extend it with role-specific columns, \texttt{Expert} publishes an expert entry in the public directory, and \texttt{FreelancerSkill} joins a freelancer to the \texttt{Skill} catalogue. \texttt{PortfolioItem}, \texttt{SocialLink}, \texttt{Certificate}, \texttt{IdVerificationDocument}, \texttt{ProfileRevision}, \texttt{CvAnalysis}, \texttt{FreelancerExperience} and \texttt{FreelancerEducation} hang from the profile. AI indexing and matching are tracked separately through \texttt{DocumentProcessingJob}, \texttt{EmbeddingIndexRecord}, \texttt{Recommendation} and \texttt{EmbeddingOutboxEvent}.
    \item \textbf{Jobs} --- \texttt{Job} belongs to a client and is classified through \texttt{JobJobCategory} (\texttt{JobCategory}) and \texttt{JobSkill} (\texttt{Skill}). \texttt{JobBookmark}, \texttt{RecentlyViewedJob}, \texttt{SavedSearch} and \texttt{JobAlert} record the browsing behaviour of a freelancer.
    \item \textbf{Proposals and contracts} --- \texttt{Proposal} references one \texttt{Job} and one freelancer; accepting it creates exactly one \texttt{Contract}, which carries \texttt{ContractTermTemplate} snapshots and a list of \texttt{Milestone} rows. \texttt{ProjectProgressUpdate}, \texttt{SharedFile} and \texttt{MilestoneFile} document the work in progress, while \texttt{MilestoneSubmission} (with \texttt{MilestoneSubmissionFile}) records the deliverable and its review decision.
    \item \textbf{Payments} --- \texttt{Transaction} stores every Stripe movement (funding, release, refund, platform fee, dispute fee) with its payment-intent identifier, and \texttt{Invoice} holds the invoice issued per contract. Money is never derived: the escrow balance of a milestone is the sum of its transactions.
    \item \textbf{Disputes} --- \texttt{Dispute} is opened on a contract or a milestone, \texttt{DisputeEvidence} collects the attachments of both parties, \texttt{DisputeFee} records the fee charged to open it, and \texttt{DisputeDecisionReview} stores the request of a party that asks for the decision to be reconsidered.
    \item \textbf{Reviews} --- one \texttt{Review} per completed contract, answered by at most one \texttt{ReviewResponse}.
    \item \textbf{Messaging and notifications} --- \texttt{Conversation} groups the \texttt{DirectMessage} rows exchanged by two accounts (pin and read state are kept on the message and on the conversation), and \texttt{Notification} feeds the in-app bell.
    \item \textbf{Community forum and configuration} --- \texttt{ForumCategory} contains \texttt{ForumPost}, a post contains \texttt{ForumComment}, and \texttt{ForumLike} / \texttt{ForumReport} attach reactions and reports to posts or comments. \texttt{ForumPost} and \texttt{ForumComment} may also store reviewer metadata for moderated content. Administrators manage reports through \texttt{ModerationQueue} (while \texttt{BannedKeyword} is reserved in the schema and currently unexposed by the API); platform-wide configuration lives in \texttt{SystemSetting}, \texttt{AnnouncementBanner} and \texttt{AdvertisementBanner}.
\end{itemize}
